Verdict: feasible as a coordinated PC update and DLC release; not as a normal guest update on an unchanged recomp.

Verdict and meaning of “Title Update 3”

A two-part user rollout is feasible, but an ordinary Xbox Title Update cannot replace our current native HarmonyRecomp changes on its own. The practical route is an unofficial PC “TU3” update bundle containing the matching native runtime changes, plus the Nathan DLC. A literal 000B0000 Xbox update requires a separate guest-code port and still needs matching ahead-of-time native compilation for HarmonyRecomp.

This assessment targets the current local ReXGlue 0.8-based build. It is a source/package audit, not a working TU3 prototype. No game binaries, saves, DLC data or update packages were changed for this assessment.

What the existing loader actually does

The installed official TU2 is a 000B0000 STFS package. Read-only enumeration found default.xexp (720,896 bytes), six base-character .dllp patches, shared item tables, text and art. The format can carry guest patches and replacement data; the existing pipeline already supports that part.

build.py:step_title_update() extracts the update over assets, requires default.xexp, and regenerates native code with REX_XEX_APPLY_PATCHES. OnLoadXexImage() enables the same patching at runtime so guest data/layout matches the compiled image. This is not runtime recompilation of arbitrary new PPC instructions.

ReXGlue’s own code/data loading documentation states that XEX images supply runtime layout/data while execution goes through prebuilt native function pointers. The local generated sub_836E4018 literally assigns ctx.r3 = 12; it does not fetch/interpret the original PPC li instruction from guest memory.

dlc.cpp installs only packages in the built DLC list; unknown/uncompiled packages are skipped or removed from the installed content set. The generated registry maps 117 guest modules to native libraries, including Nathan. A new guest DLC DLL does not automatically supply its corresponding compiled PC DLL or register itself.

Packaging location and executable format are different questions. Our Nathan logic compiled into harmonyrecomp_dllTest12.dll is PC machine code even though it belongs to the DLC target. Its source is not currently compiled into the Xbox dllTest12.dll in the package. Moving a C++ file or adding it to an STFS archive will not make either runtime execute it.

Likewise, moving the main executable’s strong overrides into Nathan’s native DLL is not a complete solution: existing generated calls and weak-alias optimizations must be prepared to dispatch to a registered callback. The current same-shard fixes demonstrate why a compatible host bridge is necessary.

The unfinished combinations do not make the two-package distribution goal impossible. They do prevent us from promising that today’s shared hooks will be the final frozen TU3. Persistent actors, damage absorption, transformed movement/hitboxes, attack replacement, targeting, drops and cleanup reach more systems than the current stat/whip implementation.

Recommended shared capabilities: character-identified input/state callbacks; outgoing/incoming damage and element policies; MP/HP/mastery/drop queries; actor spawn/update/contact/destruction; render/palette routing; native equipment/text policy; and versioned save/network state. Keep individual card definitions, artwork and effect controllers with Nathan. Future executable behavior still requires matching native DLC code unless a specifically implemented scripting/behavior runtime supports it—tables alone cannot express arbitrary new AI or transformations.

Concrete resource constraint

Resolved after the initial assessment: the body now has 3,217 frames instead of 45,975. Native shader palette-row offsets replace all 80 shade/fade geometry copies, while 377 clipped effect-layer frames retain exact visible pixel priority. The build reclaims 42,758 entries and leaves 62,318 under the 65,535-frame count limit. Future canonical body frames add at most one effect frame; shade count no longer multiplies geometry. Larger independent actors can still use separate sprite resources.

A 16-slot per-player object pool, native terrain queries, fire absorption, sword routing and subweapon Item Crash adapters now exist; the current allocation is 8,192 bytes. New state fields still need a versioned allocation contract rather than ad hoc extension offsets. New guest projectile/familiar DLLs need native module registration/codegen; reusing existing actor primitives reduces that burden but does not remove behavior work. All clients must agree on card selection, costs, actor state and update versions for multiplayer.

Recommended architecture and rollout

Practical near-term release

Use an explicitly named Unofficial TU3 for HarmonyRecomp PC update bundle. It installs the matching EXE, native modules, shared update data and compatibility manifest. Distribute Nathan’s package as the separate DLC deliverable, with its native module installed automatically if placed there. Users should never manually edit tables, copy individual DLLs or patch saves. This is a PC update bundle, not a promise that a normal Xbox 000B0000 file alone updates an arbitrary existing recomp build.

Maintainable long-term split

Prepare a compatible host with shared extension points, and keep Nathan-specific implementations in a versioned DLC/native module. The host must resolve registration and dispatch correctly, including calls currently folded directly to local generated implementations. Gate extension use by loaded character/package and preserve native fallback behavior with Nathan absent.

Define the missing DSS behaviors before freezing the extension API. Implement representative difficult cases—a projectile pair, an elemental absorption pair, a persistent familiar and a transformation/state-changing pair—then assess whether the common callbacks suffice. It is not necessary to finish all 100 effects before a first release, but unsupported pairs must remain explicitly unavailable and new API requirements may require another update.

If a genuine guest Title Update is a requirement

Port shared wrappers to PPC guest code, including ABI-correct calls, trampolines/new code placement, actor callbacks and original fallbacks. Port character-only C++ to the guest Nathan DLL as well. Author a valid cumulative XEXP/DLLP update against the intended original image/version and retain TU2’s required behavior and data. Rebuild HarmonyRecomp from that patched guest image. This is a separate substantial engineering project, not repackaging the current source.

Loader changes and proof gates before a rollout commitment

  1. Update identity: replace “largest file wins” with explicit version/compatibility selection. Current build.py chooses max(package size), hardcodes the TU2 codegen config, and runtime labels any default.xexp build “2.04”. File size is not a reliable unofficial version ordering.
  2. Cumulative base: the current setup selects one update, not a TU2→TU3 stack. A real TU3 must preserve TU2 compatibility and match the expected base image/version. Do not assume a new delta targeting an already patched image will be layered automatically.
  3. Native/guest agreement: check base and patched image hashes, native API/build ID, target architecture, generated module paths and frame/state versions. Reject mismatches clearly. Loading different patch data with old compiled functions can silently execute the wrong logic.
  4. DLC installation: extend package/native module discovery and registration. Ensure the built list does not remove Nathan or new actor modules as uncompiled content.
  5. Clean content test: fresh TU2 base + proposed update + Nathan only; no development loose files or pre-edited unrelated DLC. Verify shared permission routing, not just the existing edited install.
  6. Saves: test fresh profiles, existing profiles with no Nathan data, current test saves and rollback. Use game-side migration; decide release card acquisition rather than granting every test card by accident.
  7. Future-DSS prototype: exercise projectile, shield/interception, absorption, familiar, transformation and stat/drop callbacks before committing to a frozen API.
  8. Multiplayer: replace the coarse 2.04 label with a TU3 build fingerprint plus DLC/API/content versions. Current lobby distinguishes game versions and treats some DLC differences as playable; incompatible DSS builds must not be accepted as identical.
  9. Packaging validation: no local STFS/XEXP authoring workflow has yet produced a TU3. The installed tools prove extraction/patch loading and direct XEX editing, not completed update-container construction. A PC bundle needs its own manifest/install/rollback proof.

Readiness: a PC two-deliverable rollout has a clear implementation route. A literal drop-in guest TU3 on an unchanged recomp is a no-go. A genuine guest-code TU3 is technically plausible for gameplay after a port and matching rebuild, but is not validated by this audit.
